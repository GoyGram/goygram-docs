# Архитектура и поведение во время работы

У GoyGram единое ядро приложения с опциональными транспортами Bot API и MTProto. Оба кормят внутреннюю шину событий; диспетчер превращает обновления в объекты событий и вызывает зарегистрированные наборы обработчиков.

## Порядок запуска

`run()` сначала стартует диспетчер и FSM-движок. Затем, если настроен Bot API, запускает поллинг. Для MTProto — бутстрапит авторизацию, поднимает MTProto-соединение с reader'ом, запрашивает состояние обновлений и ждёт `stop()`.

## Динамическая диспетчеризация

Обёртки методов Bot API и MTProto резолвятся через `__getattr__`, а не генерируются как Python-методы:

- `send_message(...)` превращается в Bot API `sendMessage`.
- `mt_messages_get_dialogs(...)` превращается в MTProto `messages.getDialogs`.

Это значит, что новые методы схемы не требуют релиза Python-обёрток, но и валидация аргументов следует за транспортном/схемой, а не за статическими Python-сигнатурами.

## Схема и Rust-расширение

Слой MTProto инициализирует данные TL-схемы через Rust-расширение и менеджер схемы. Сериализация использует Rust-расширение, когда оно доступно. У данных схемы есть встроенный/bootstrap-путь и путь обновления с сервера; приложениям не следует завязываться на внутренние форматы кэша схемы.

## Маршрутизация датацентров

MTProto без явного хоста запрашивает динамическую конфигурацию датацентров и выбирает DC 2. Встроенный эндпоинт используется только как фолбэк, если поиск не удался. Загруженный vault затем может выбрать сохранённый в нём датацентр.

## Самовосстановление обновлений

Курсоры обновлений (`pts`, `qts`, `date`, `seq` и per-channel версии) персистятся между запусками. После разрыва соединения или `updatesTooLong` запускается `getDifference` циклом по слайсам, для каналов — `getChannelDifference`; просроченные `file_reference` обновляются и запрос повторяется. Всё это происходит автоматически, без настройки.
