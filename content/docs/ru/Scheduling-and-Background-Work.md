# Планировщик и фоновая работа

GoyGram сознательно держит планирование простым: клиент владеет Telegram I/O, а ваше приложение — фоновыми задачами и политикой отмены.

## Периодическая задача

Фоновую работу создают из async-точки входа программы, а клиент запускают в том же event loop:

```python
import asyncio
from goygram import GoyGram

app = GoyGram(bot_token="TOKEN")

async def heartbeat():
    while True:
        await app.send_message(chat_id=123456, text="ещё жив")
        await asyncio.sleep(3600)

async def main():
    task = asyncio.create_task(heartbeat())
    try:
        await app.run()
    finally:
        task.cancel()
        await asyncio.gather(task, return_exceptions=True)

asyncio.run(main())
```

Держите ссылку на каждую созданную задачу. При остановке отменяйте задачи и дожидайтесь их с `return_exceptions=True`, чтобы отменённый sleep не замаскировал реальную ошибку остановки.

## Встроенные задания: `every` и `later`

Для двух самых частых сценариев GoyGram оборачивает `asyncio` за вас — без декораторов, хранилища заданий и классов-обёрток. Оба принимают синхронные и async-функции и возвращают лежащий в основе `asyncio.Task`:

```python
# крутиться вечно каждые N секунд
task = app.every(3600, heartbeat)
task = app.every(30, poll_api, "feed-id")      # позиционные аргументы пробрасываются

# выполниться один раз после задержки
task = app.later(10, remind, "проверить духовку")  # ключевые аргументы тоже
```

`every` никогда не накладывает два запуска одного задания: каждый тик ждёт завершения предыдущего вызова и только потом спит. Остановить задание — отменить возвращённый task. Хелперы держат сильную ссылку на задачу, поэтому периодическую работу нельзя собрать сборщиком мусора на ходу.

## Диалоги (conversations)

`conv_wait` ставит обработчик на паузу до следующего сообщения из того же чата — поток «вопрос/ответ» без FSM-сантехники:

```python
@app.on_cmd("name")
async def ask_name(msg):
    await msg.reply("Как тебя называть?")
    answer = await app.conv_wait(msg.chat_id, timeout=60)
    if answer is None:
        await msg.reply("Время вышло, забей.")
        return
    await msg.reply(f"Приятно познакомиться, {answer.text}")
```

`conv_wait(chat_id, user_id=None, filt=None, timeout=60)` умеет ждать конкретного пользователя или фильтровать ожидаемое сообщение. В диалоги попадают только чужие сообщения; собственные сообщения бота продолжают идти в обработчики как обычно. Новый `conv_wait` на тот же чат заменяет старое ожидающее. Ожидающий резолвится до обычных обработчиков, поэтому шаг диалога может «съесть» сообщение, которое иначе запустило бы и `on_msg`.

## Не блокируйте обработчики

Обработчики делят event loop с Bot API-поллингом и чтением MTProto. Не запускайте блокирующий I/O или тяжёлые вычисления прямо в обработчике. Берите асинхронную библиотеку, отправляйте работу воркеру через очередь или выносите CPU-нагрузку в `asyncio.to_thread` / пул процессов.

```python
@app.on_cmd("report")
async def report(msg):
    result = await asyncio.to_thread(build_report)
    await msg.reply(result)
```

## Истечение состояния

[Записи состояния](/docs/Keyboards-Formatting-and-State) могут получать TTL. Рантайм GoyGram сам запускает цикл очистки FSM, поэтому просроченные записи исчезают, пока активен `app.run()`.

Для внешних планировщиков (systemd timers, cron, очередь воркеров) держите старт Telegram-клиента отдельно от реализации задания и инициализируйте только транспорт, который заданию нужен.
